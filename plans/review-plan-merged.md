# MDE 规划审查：哪儿有问题、怎么改

## Context

用户要求审查 `PLAN_MERGED.md`（MDE v1 合并规划，项目现行唯一立场来源），提出改进建议与落地方案。
本仓库为纯规划仓库；实现代码在兄弟仓库（原 `~/mdx`，已更名为 `~/mde`）。审查基于四份文档：`PLAN_MERGED.md`、`PLAN.md`、`comparison.md`、`AGENTS.md`。

## 总评

`PLAN_MERGED.md` 是一份质量很高的收敛文档：立场已冻结（ZIP + manifest）、三层兼容、渲染管线顺序、负向/安全测试矩阵都到位。
剩余问题集中在三类：**（一）规范内部自相矛盾或完整性缺口、（二）北极星决策悬置阻塞落地、（三）验证/落地路径有空档**。以下按严重度分级。

---

## 一、Blocking 级问题（规范自相矛盾 / 完整性硬伤）

### 1. `entrypoint` 二义：固定命名 vs manifest 声明
- `§2.1 冻结清单 #2`：主文档「固定为 `document.md`」
- `§3.2 manifest 最小结构`：含 `entrypoint` 字段
- **冲突**：若 manifest.entrypoint 可指向任意包内文件，则「固定命名」是假约束；若固定命名，则 entrypoint 字段冗余。
- **建议**：`manifest.entrypoint` 为唯一真源；`document.md` 降级为「缺省时的默认值/惯例」，规范正文只写一条，不写两条。

### 2. 符号转义机制「推到实现期确定」违反 Phase 0 完成标准
- `§4.2`：「转义机制需在解析器测试后确定」
- `§7 Phase 0 完成标准`：「所有未决事项有默认值」
- **冲突**：转义是规范级决策（决定 Markdown 原生反斜杠 `\` 与 `(tm)` 转义的交互），不能推迟到实现期；否则两个实现者会对同一 `\(tm)` 产生不同语义。
- **建议**：在 Phase 0 就写死转义规则（建议默认 `\` 前缀转义，与 Markdown 原生反斜杠同字符，在符号转换器内优先于扩展解析）。

### 3. 符号「词边界规则」未固化进规范正文
- `§12.3`（Sisyphus 审查）提出：「仅普通文本、前后空白或中文标点时才转换」，但 `§4.2 正文` 没有这条规则。
- **冲突**：审查补强没有合并回规范正文，正文仍是「只作用于普通文本」，缺「词边界」细节。实现者只读 §4.2 会漏掉误伤防护。
- 连带：`§4.2 core profile` 含 `...→…`，而 `§12.3` 恰恰点名 `...` 是误伤高危（路径/命令/版本号）。**core 集应剔除 `...`，移到 extended**，或明确 core 对 `...` 也走严格词边界。

### 4. Unicode 规范化（NFC/NFD）缺失 —— 跨平台可重复构建硬伤
- `§3.3` 只提「大小写冲突、重复分隔符、NUL」，未提 Unicode 归一化。
- **问题**：macOS APFS 用 NFD（`é` = `e`+U+0301），Linux 多数用 NFC（`é` = U+00E9）。同一个逻辑文件名在两端字节不同 → 打包到 manifest 的路径与 SHA-256 在另一平台对不上，`validate` 全部误报。
- **建议**：规范写死「路径与文件名在打包前统一 NFC 归一化再入库」；同时显式拒绝「归一化后相同但字节不同」的重复路径。

## 二、High 级问题（北极星决策悬置，阻塞落地）

### 5. §13 六项未决是命脉决策，但全悬置 + 无拍板顺序
- `§13 #1 产品定位`、`#2 实现语言` 是关键路径：不拍定位，无法写 §15 成功指标；不拍语言，Phase 1 CLI 无法开工。
- **问题**：文档给了「建议默认」，但没给「哪几项必须在下个里程碑前拍板、其余可并行」的排序。规划停在「技术已收敛、产品/工程未收敛」。
- **建议**：把 §13 拆成「P0 阻塞项（#1/#2，Phase 0 启动前必须拍板）」+「可并行项（#3/#4/#5/#6，Phase 1 前拍板即可）」，每项标注拍板截止点。

### 6. 文档治理（§14）仍是「建议」，冲突源未真正消除
- Codex 审查把「三文档立场冲突」列为 #1 高风险，§14 给了治理建议，但仓库里 `PLAN.md` / `comparison.md` / `PROPOSAL_COD.md` 仍在，立场冲突源未物理移除（仅 AGENTS.md 更新了 NOTES）。
- **建议**：给三份旧文档头部加 deprecation banner（「历史输入，立场已被 PLAN_MERGED.md 取代，勿引用作结论」），并把 §14 从「建议」改为「已执行 checklist」。

## 三、Medium 级问题（验证 / 落地空档）

### 7. 性能无基线门槛，导致性能永远「不可能失败」
- `§8.7`「指标实测、不预先写死倍数」方向正确，但 Phase 1 完成标准里没有任何资源上限（解压上限、单资源随机读延迟、峰值内存）。
- **建议**：Phase 1 完成标准加一条硬约束：「解包资源总数 N、单文件 M 字节、总解压 S 字节、include 深度 D 的上限必须可配置且默认存在」，功能正确性之外补「资源上限可生效」的验证（绑定 §9 炸弹/放大缓解）。

### 8. 「最小示例包」无具体结构定义
- Phase 0 完成标准要求「最小示例包」，但正文未给其内容。
- **建议**：Phase 0 产物清单里补最小示例包骨架（含 1 张图片 + 1 级 include + core 符号 + 1 个错误样例），与 §8 测试集共用。

### 9. 「单一参考实现」vs「两个独立实现者」时间线不清
- `§7 说`「先单一参考实现，跨语言测试向量」，Phase 0 完成标准却要求「两个独立实现者仅凭规范生成同等语义包」。
- **风险**：若第二实现者拖到 Phase 3，规范会「实现即规范」——规范缺陷被参考实现掩盖。
- **建议**：明确「Phase 0 的规范评审由第二个独立实现者（哪怕人肉按规范手写一个最小包）独立验证」，不等 Phase 3 才引入第二视角。

### 10. SVG 渲染安全未定
- `§4.1` SVG 在资源白名单内；`§9` 缓解是「渲染器默认清理」。
- **问题**：SVG 若内联进 HTML = XSS 面；若 `<img src>` 引用则相对安全但等于不做内联。§6 管线第 6 步「安全清理」没定义 SVG 的渲染方式。
- **建议**：规范写死「SVG 默认作为 `<img>` 引用渲染（不内联），`--unsafe-inline-svg` 才内联」。

## 四、Low 级问题（一句话即可，暂缓）

- **L1** 外部 URL 图片（§4.1 默认保留外链）渲染时 `<img src="https://...">` 造成 referrer/IP 泄露，需在渲染器加 `referrerpolicy="no-referrer"`。
- **L2** 风险表缺「项目孤儿/无维护者」条目（§9 有 12 条但没这条）。
- **L3** ZIP 库跨实现差异（符号链接处理、DEFLATE 字典/方言）会影响「两个实现者产出同等包」，需在互操作测试里锁定具体库版本或行为契约。
